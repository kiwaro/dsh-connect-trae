# DSH 插件发布经验备忘

本文整理上游发布过程及 `dsh-subagent-default-model` 的工程经验。历史命令的输出、处理时长和错误码仅代表当时环境。当前执行步骤见 [发布流程](../RELEASING.md)；本次文档审核没有执行公开发布或浏览器授权。

## 1. 发布环境核对

发布前检查当前仓库配置和账号：

```powershell
git config user.name
git config user.email
git remote -v
npm whoami
```

提交署名由执行者与仓库约定决定，源码版权声明按实际权利归属保留，两者分别核对。历史署名与发布账号请按 LICENSE 和发布记录核对，不作为其他工作区的默认配置。

原环境通过 `127.0.0.1:7897` 代理访问服务。换机器后按实际网络配置，避免把历史代理直接写入全局设置。读取 npm 配置时只检查所需字段，保留凭据隐私。

## 2. 发布步骤速查

1. 运行 `pnpm run check`，核对许可证和本次变更。
2. 更新版本号、变更记录日期和双语 README。
3. 创建带说明的版本标签，核对标签指向的版本提交。已经推送或对应包已发布的标签保留原指向。
4. 使用 `npm pack --dry-run` 核对实际文件清单，确认没有凭据和临时诊断文件。
5. 按用户授权执行推送与发布，并根据命令提示完成身份验证。
6. 查询目标版本及授权的发布标签，随后核对包内容与版本源码。
7. 在 DSH 中验证安装、注册和实际受影响功能。

完整命令及失败处理以 `RELEASING.md` 为准。文件白名单以当前 `package.json` 为准，历史文件数量不能用于判断新版本是否完整。

## 3. DSH 插件工程检查

### 3.1. 入口与客户端服务

`package.json` 应导出 `./package.json`，让 DSH 能读取插件元数据。客户端激活需要的服务在 `src/client/index.tsx` 声明，打包注入包在 `package.json` 的 `dsh.client.inject` 中声明；两处分别核对。客户端测试应覆盖设置卡片和插槽注册。

历史记录称 DSH 0.1.1-rc.2 移除了设置命名空间白名单。该结论属于对应版本，升级后按实际依赖与运行结果验证，避免为旧限制添加无效补丁。

### 3.2. 安装与更新

本机 Windows 工作区使用实体安装副本。构建工作区后需要同步实体安装目录及 desktop 的依赖副本，再重启 DSH，详见 [本地部署记录](LOCAL-DEPLOYMENT.md)。早期 macOS 开发使用 `link:` 软链，重建会改写 DSH 正在加载的文件；对应风险见 [开发说明](../DEVELOPMENT.md)。

插件安装使用 DSH 的正式命令，让 DSH 维护依赖与 bundle 登记。已有实体副本更新产物时，先核对部署方式；每次更新都重新安装整个依赖树可能引入额外变更。

### 3.3. 配置与版权

`cordis.patch.yml` 登记插件入口，保留用户已有的默认模型。包内许可证、版权元数据与 README 的声明应与实际来源一致。设置是否热加载由具体实现决定；更新插件代码后按部署流程重启并验证。

## 4. 发布后的 DSH 验证

使用独立验证 profile 安装明确的目标版本，再检查设置卡片及模型注册。短流式对话会消耗额度，按用户授权执行。验证完成后记录实际版本、安装来源和结果；仅有进程启动或模型目录出现，不能证明对话链路可用。

## 5. 常见问题

| 现象 | 检查方法 |
| --- | --- |
| 设置卡片没有出现 | 核对当前 profile、插件来源、元数据导出、客户端服务与重启结果 |
| 保存按钮不可用 | 对照具体配置的必填项和校验提示检查 |
| 发布命令报告身份验证错误 | 保留该次日志，先查目标版本是否已经存在，再按当前 CLI 提示处理 |
| `latest` 仍是旧版本 | 单独查询目标版本，再结合发布受理日志判断是否仍在处理 |
| 模型使用不符合预期 | 核对供应商、模型配置及实际请求路由 |

## 6. 历史发布事件与处理方法

### 6.1. 2.0.5 的传播延迟

2026-09-22 发布 2.0.5 时，命令报告 `PUT 202`，并提示包正在处理。随后目标版本元数据与包下载地址一度返回 404，`latest` 仍是 2.0.4。旧版包可下载只能证明旧版已经传播，无法据此判断新版发布失败。

处理完成后，线上包的 SHA-1 为 `51bc1815d171424906cac8e0ea438c48913d0b1f`，与当次发布输出一致；当时包内 12 个文件与 `v2.0.5` 标签逐文件核对一致。该事件说明需要区分“已受理”“已公开可读”和“内容已经核验”三个状态。

保留当次发布日志，再查询精确版本。能安装目标版本表示该版本可读，文件内容仍需与目标源码核对。镜像同步速度和旧包可下载状态只提供辅助信息。

### 6.2. 沙箱与依赖状态错误

历史环境中，`npm whoami` 曾因沙箱限制报告 `EPERM`；放宽该次执行环境后同一命令成功。另一次 `pnpm run check` 遇到 `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`，当时也与执行环境有关。

这些是具体事件，不能推断所有同名错误都由沙箱引起。出现错误时检查具体路径权限、工具配置和依赖状态，再决定修复方式。避免在原因未明时修改用户目录权限或重装整棵依赖树。

需要绕开包管理器的启动检查时，可以直接执行现有的 TypeScript、Vitest 与构建工具；仍需核对执行命令覆盖原检查内容，并使用平台支持的启动方式。

### 6.3. macOS 的命令超时

历史 macOS 环境没有安装 `timeout`，因此 `timeout 45 git fetch` 在启动阶段失败。需要命令超时时，使用当前执行工具提供的超时参数，或确认系统已有适用程序；参数名称以实际工具为准。

### 6.4. 发布日期与时区

2.0.5 发布记录曾误用了 issue 的 UTC 创建日期 `2026-09-21`。该次操作按 Asia/Shanghai 计算，实际发布日期是 `2026-09-22`。

变更记录日期取实际发布时刻在约定时区中的日期，并在创建版本标签前定稿。已经公开的标签保留原指向，文档修正在后续提交或版本中记录。

### 6.5. 新增测试是否执行

2.0.5 当时新增了 4 项测试，基线为 236 项，修改后为 240 项。测试总数没有变化时，需要检查新增用例是否被配置包含，或是否同时删除了旧用例。

优先使用详细测试报告核对新增用例名称。需要运行旧基线时，在独立临时检出目录执行，避免为了比较测试数而暂存、弹出或覆盖用户当前改动。测试结果通过仍需确认目标用例实际执行。

### 6.6. 标签、源码与包内容

带说明的标签有自己的对象哈希，它与指向的提交哈希可以不同。使用以下命令核对标签所指提交：

```powershell
git rev-list -n 1 vX.Y.Z
git rev-parse HEAD
```

推送前先更新远程引用，再检查分支关系。新文件还需检查是否被忽略；`lib/` 可以不进入 Git，却通过发布白名单进入 npm 包。

核对发布内容时逐文件比较。重新打包的压缩文件可能因打包工具或元数据不同而具有不同哈希；仅此差异不能证明包内文件不同。线上包与当次发布日志的哈希一致，则支持两者属于同一份上传内容；源码一致性仍由逐文件检查确认。

### 6.7. 2.4.0 在凭据报错前已上传

2026-09-29 的本地发布记录中，`pnpm publish` 报告：

```text
[ERR_PNPM_OTP_NON_INTERACTIVE] The registry requires additional authentication,
but pnpm is not running in an interactive terminal
```

随后用户重发得到 `E409 You cannot publish over the previously published versions: 2.4.0`。历史 registry 记录显示：

```text
registry.time['2.4.0'] = 2026-09-28T20:12:26.305Z
registry.dist-tags = { latest: '2.4.0' }
```

该次包已公开，重复发布才被拒绝。此事件只证明这一轮的报错与实际上传状态不同，不能概括为所有 CLI 都固定先上传再验证。遇到凭据错误时，结合精确版本查询与该次日志判断。

`previously published versions` 与 `previously staged version` 是不同错误原文，保留完整信息再判断版本状态。

### 6.8. 执行授权与身份验证

检查、文档修改和制作候选包按开发授权执行。推送、公开发布与其他对外写入按用户明确授权执行，已有有效授权无需重复索取。

需要用户交互验证时，说明当前等待的具体动作。凭据保留在原有配置与验证流程中，避免把令牌复制到命令正文、聊天或项目文件。谁执行发布命令由本次授权和实际交互能力决定。

### 6.9. 2.5.0 的发布前验证失败

2026-10-01 发布 2.5.0 时，非交互命令在上传前遇到身份验证要求。用户在交互终端执行后，日志出现以下轨迹：

```text
PUT 401 → web-auth → PUT 202 → processing
```

当时从受理到发布标签更新约 90 秒。这个时长只属于该次事件。日志出现 `PUT 202` 表明已受理，仍需等待公开查询及内容核验。

缺少 `PUT` 行时，先确认日志完整性与日志级别；仅凭日志中没有某行，无法证明请求一定没有到达 registry。结合命令错误、完整日志和目标版本查询判断，避免把“尚未确认”提前报告为“发布失败”。

### 6.10. 4.6.2 的 E404 与一次性口令

2026-10-27 发布 4.6.2 时，命令报告 `E404 Not Found`，当时通过进一步调查发现缺少一次性口令。用户在交互终端完成浏览器验证后发布成功，正常轨迹仍为 `401 → web-auth → 202`。

该事件不能推出所有“404 且没有 web-auth”都表示缺少口令。相同错误还需要结合包名、权限和 registry 配置判断；`npm whoami` 成功也不能单独证明账号有发布权限。

原记录曾展示从 `.npmrc` 抽取令牌并手工发送 PUT 的探针。本次修订移除该可执行示例，保留其观察结果：当时探针返回 401，响应要求一次性口令。当前排查使用正式 npm 命令及其脱敏日志，避免将配置中的令牌带入命令行。
