# 账号设备绑定与 4017 排查

## 1. 依据与边界

参考 wild-work 的提交 `a3c6993` 及 issue #60 的维护者回复：其历史对照记录将多账号共享设备号与部分 4017 风控关联起来。原 issue #70 当前不可访问，结论依据来自仍可读取的提交、维护者回复与回归测试。该样本不能证明所有 4017 都由设备共享引起。

参考来源：<https://github.com/rockswang/wild-work/commit/a3c6993cc1ec76bea6075874238e2a4dfdabbc6a>、<https://github.com/rockswang/wild-work/issues/60#issuecomment-6051679763>。

本插件读取已有 Trae 登录，不创建新的注册设备，不自动随机替换设备号。设备身份与刷新签名密钥必须属于授权时的同一份登录记录。

## 2. 已实现的处理

1. 从本机客户端读取登录时，使用同一份存储快照解析凭据和设备身份，避免切换账号期间混读。
2. 设备身份随账号保存到私有凭据副本，令牌刷新保留该绑定。重新登录产生更晚到期的有效凭据时，整体更新凭据与设备；同一令牌的旧副本可以补齐设备绑定，不为不同令牌猜测设备。
3. 普通对话、目录、账号池换号、令牌刷新及签到都优先使用实际请求账号保存的设备身份。签到将令牌和设备头固定到一次凭据读取，指定账号的操作也不再借用当前选择的客户端。
4. 状态接口只提供是否绑定及共享账号名称，不返回设备号、机器号或签名密钥。账号列表与账号池显示缺少绑定或共享设备的提示；提示不保证重新登录能解除风控。
5. 导出文件可携带设备绑定和签名私钥，导入时校验字段与区域。文件应按密码保管，预览接口不返回这些秘密。
6. 签到遇到 9095 后，仅跳过相同设备的后续账号；其他已绑定设备继续执行。缺少绑定的旧账号按同一个兼容设备组处理。界面不再因为其他设备的失败锁定已有独立绑定的账号。

## 3. 旧账号如何处理

旧凭据缺少设备绑定时仍按原有安装身份解析，以免升级造成账号全部失效，同时显示未绑定提示。只有能确认同一令牌或完整的新登录来源时才写入绑定。

若 4017 持续出现，用户可在 Trae 重新登录该账号，再刷新插件账号列表。导入账号应使用来源端导出的完整凭据与设备绑定。不要仅修改设备号，也不要反复重新登录消耗设备名额。

## 4. 验证

`tests/account-device.spec.ts` 覆盖设备快照持久化、刷新保留、重新登录更新、导入导出、备用账号请求头、签到单次读取、共享诊断和设备级签到隔离；`tests/account-device-render.spec.tsx` 覆盖提示与账号行结构。对账号身份优先级及私有副本读取进行了反向变异验证。

这些回归使用合成夹具，不代表真实账号的 4017 已解除。真实效果需要在正常请求中观察。

## 5. 本地试装记录（2026-11-08）

当前旧账号仍缺少可确认的设备绑定，因此这里只确认部署生效，不确认真实 4017 已解除。需要在官方客户端重新登录后刷新列表，再观察正常请求。发布隐私检查有 14 项通过，截图 OCR 因缺少后端跳过；本次未修改图片，未进行 npm 发布。
